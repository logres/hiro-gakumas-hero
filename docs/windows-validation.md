# Windows OCR 验证记录

日期：2026-11-06。这里记录 Windows OCR provider 的已验证范围，不代表 DMM 截图、输入、窗口恢复或完整游戏流程已经通过验收。没有向游戏发送输入。

## 配置

在启动应用的同一个 PowerShell 进程中显式选择模块：

```powershell
$env:HIRO_OCR_BACKEND = 'hiro.platforms.windows.ocr'
```

模块提供 `ocr(img, *, scale=3.0, languages=('ja-JP', 'en-US'))` 和相同参数的 `ocr_boxes`。输入为 BGR 图像；返回框是原始图像左上原点的 `(x1, y1, x2, y2)` 像素坐标。内部放大后的四点框按实际缩放尺寸还原并裁到原图范围。

需要已安装的 play 环境；本次使用项目 `.venv` 的 Python 3.10、kotonebot==0.20.1、rapidocr_onnxruntime 1.4 系列及 ksaa-res 自带资源。provider 通过 `kotonebot.util.lf_path` 定位 `models/japan_PP-OCRv3_rec_infer.onnx` 和 `models/en_PP-OCRv3_rec_infer.onnx`，不下载模型。RapidOCR 使用检测与识别，关闭方向分类，CPU intra-op=2、inter-op=1。

默认日文+英文请求选择日文模型；英文单独请求（如公共数字 OCR 辅助函数）选择英文模型。支持 `ja` / `ja-JP`、`en` / `en-US` / `en-GB`，大小写不敏感并接受下划线。未知语言、空语言列表和非正/非有限 scale 会报错。依赖或资源缺失会抛出可用性异常，不悄悄回退中文识别模型。

## 自动测试

执行 `.venv/Scripts/python.exe -m pytest tests/test_windows_ocr.py -q`：**10 passed**。

测试通过模拟引擎验证四点框缩放和裁边、原始置信度保留、文字投影、空结果、英文模型选择、不支持语言与非法 scale。它们验证适配契约，不衡量真实模型准确率。

## 真实引擎合成图片

使用 Pillow 在白底 RGB 图片上以 `C:/Windows/Fonts/meiryo.ttc`、48 像素黑字绘制文字；识别前转为 BGR。两次调用均使用 `scale=1`，直接加载上述本地模型运行。

| 输入与图片 | 请求语言 | 实际输出 | 置信度 | 原图框 |
| --- | --- | --- | --- | --- |
| `体力 123 テスト 456`，900×160，绘制位置 (20,20) | 默认日文+英文 | `体カ123テスト456` | 0.9456200274554166 | (11,21,497,85) |
| `123456`，350×120，绘制位置 (20,15) | `('en-US',)` | `123456` | 0.9999945958455404 | (16,20,208,76) |

这确认模型能在当前环境加载、返回文字/置信度/框，且英文数字样例识别正确。日文样例把汉字 `力` 读成片假名 `カ`，空格也未保留；不能据此宣称日文准确率达标，置信度高也不等于无误。
