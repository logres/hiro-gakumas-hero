# 决策泛化约束

目标是能适配、积累不同偶像卡版本和构筑的决策经验。先用白線リーリヤ验证端到端流程；单角色通关不等于通用决策验收。

## 通用方案的验收约束（2026-11-07）

用户再次明确：当前角色是试验载体，最终需要适配并学习不同偶像的出卡思路。新增策略能力优先表达为效果、资源、阶段与组合条件，不新增按角色名固定回合出牌的补丁。

- 共享状态描述费用、资源门槛、行动返还、持续触发、一次性消费、当前牌堆及证据可信度；角色卡版本与构筑决定策略资料的适用范围，名字本身不决定动作。
- 决策应同时比较当前收益与后续可用性。例如早期安装引擎，也须考虑剩余资源是否能支付其他已知核心卡；抽回机会未知不能当作必然抽回，也不能当作概率为零。无法证明某动作更优时记录不确定性，不用单局分数反推精确反事实。
- 经验条目至少包含机制条件、建议与例外、来源、支持及反例、版本和验证范围。先区分识别错误、机制缺失、计划错误与执行失败，再决定更新哪一层。保存日志不等于已实现自动学习。
- 泛化评估保留未用于调参的局面与构筑：覆盖同角色不同卡版本、不同角色相近机制、不同机制路线；对机制相同的候选调换槽位，检查选择是否保持语义一致；改变费用、触发条件或剩余回合，检查策略是否相应改变。未知效果必须保留未知，不能为满足名称不敏感而抹去真实身份差异。
- Codex CLI 与 API key 共用状态、策略资料、输出契约和评估集。分别记录模型与版本，协议兼容不等于决策质量相同。

推进顺序：先补齐当前局的状态和资源依赖证据，再做机制级回放与回归，随后验证其他构筑；完整培育通关与跨构筑质量分别验收。当前尚未完成自动经验更新或跨角色可用性验证。

## 通用预演后端的候选与准入

只读审查候选 [gakumas-tools](https://github.com/gakumas-tools/gakumas-tools/tree/dc39245b9247a3ec800bf5c9a017da1dfa65fcd6)（固定 SHA `dc39245b9247a3ec800bf5c9a017da1dfa65fcd6`）。目前没有安装、执行或接入该引擎。其 `StageEngine.useCard/endTurn` 提供局部状态推进，效果管理器包含条件、触发计数与持续时间，适合作为机制级验证候选；不能据 README 将它当成已验证的 H.I.F 模拟器。

- MCP 入口仅支持 contest/event/linkContest 完整初始配置，不支持 Hiro 当前中盘状态导入；引擎的状态数组之外还有触发注册。仅填资源数值不足以恢复战局。
- 卡牌升级与 customization 补丁需逐项映射，不能按同名把 Hiro 的 `++/+++` 合并为布尔升级。未知费用、定制或持续触发余量不填零。
- [真实对照说明](https://github.com/gakumas-tools/gakumas-tools/blob/dc39245b9247a3ec800bf5c9a017da1dfa65fcd6/tests/contest-fidelity.md) 记录尚未解决的得分差异；截图及期望值在公开仓库外，缺少 fixture 时相关测试不注册。因此公开测试通过不构成独立游戏正确性证明。
- 随机种子只使假设可复现，不代表真实抽牌顺序。未知概率仍须保留未知；不得以一次随机模拟输出作为精确期望分。

后续最小接入范围是离线、单动作、无随机抽牌的已验证机制。适配器先检查动作合法性、精确版本及所有相关效果是否完整；缺项返回不可预演，不能沿用引擎默认值。先对付款顺序、行动返还、回合结算及持续触发逐项建立独立预期，再比较真实前后帧。覆盖通过后才让预测作为决策辅助证据，最后考虑有限深度搜索；当前决策路径不依赖该候选引擎。

泛化验收须将机制等价与角色差异分开：重命名角色或交换手牌槽位不应改变语义选择；改变费用、行动返还、持续回合、当前牌堆或角色固有效果，则应重新评估。每项提升必须说明验证了哪些机制和版本，不能将单角色成功推广为所有偶像可用。

## 分层边界

- 平台执行：Windows/Mac 只负责观察与合法输入，不包含角色打法。
- 通用机制：卡牌/饮料/道具效果、费用、触发条件、行动预算、持续时间和信息可信度。确定规则负责合法性与可证明的局部比较；缺少模拟器时不伪造收益预测。
- 策略资料：按机制路线、偶像卡版本与阶段组织目标、组合、保留条件和例外，记录来源与适用前提。角色资料作为上下文，不在执行器中写角色分支。同一角色不同卡版本不能混为一套打法。
- 决策接口：规则、模型或将来的搜索使用相同状态和候选契约。Codex CLI 与 API key 仅替换模型传输，不维护两套策略。
- 经验更新：trace → 失败/错失机会归因 → 候选策略资料或通用规则 → 冻结局面回放与跨构筑回归 → 小范围实测 → 接受或撤回。单次胜负不自动变为规则；没有版本化经验和复核就不能称为自动学习。

## 实施与验收

当前新增内部纯视觉接口 `vision.exam_group_page_evidence.read_exam_group_page_evidence`，为后续有界滚动扫描保留同页标题/数量、完整可见卡格、局部行列和裁剪边界。重复副本保留，无标题卡格不猜归属；裁图哈希只绑定像素，不作为跨页实体ID。公共分组快照仍只向决策提供完整组。19项相关检查及真实首屏离线读取验证了手札3/3、山札15张中可见8张；尚无滚动、跨页拼接或全牌堆扫描完成证明。

1. 先在当前角色闭环：完整培育、解释动作、记录不确定性与失败点。
2. 将路线 guard 的简单结束/等待逐项替换为机制驱动决策；现有好印象专属局部启发式应标记适用范围，不能当成通用评分器。
3. 复用同一决策接口与回放工具，加入另一机制路线及同角色不同卡版本，检查角色资料是否被正确选用、是否污染其他路线。
4. 用规则基线、模型、经验更新后的冻结局面对照评估合法率、识别失败、决策理由、资源使用及实测成绩。只有真实覆盖的路线标记可用。

尚未完成：版本化策略资料检索/更新闭环、跨路线验证、完整选拔与本战通关。当前通用 prompt 和饮料选择只是基础，不能宣称已有自学习系统。

### 真实决策接口的合成泛化评估

`tools/check_synthetic_generic_decisions.py` 生成28个完全人工的封闭局面，经过实际BattleState序列化、generic提示词及RuleLLMAdvisor链路。覆盖即时得分、支付资源与回合结算、行动返还门槛、持续收益期限；交换槽位和合成展示标签，判据按卡身份判断。展示标签变化只检验名字敏感性，不代表真实不同偶像的固有效果已覆盖。每例明确假设；未来仅能skip等前提是人工条件，不能当作游戏抽牌模拟。

默认零模型调用，输入和独立算术判据分别保存哈希。报告保留首次模型回答、全部调用原文与错误、重问及最终流程结果；规则、mock或guard纠正不计首次模型正确。新工具与回放组合20项测试通过。

以Codex CLI/gpt-6.1-sol、generic1.11执行8个不同案例，每例一次调用，首次动作与必要后续计划全部符合判据，来源哈希始末一致。包括即时得分的标签/槽位变换一对，以及费用0/10、可支付资源3/2、剩余回合3/1三对条件变化，模型均随条件改选。只测了28例中的8例，未证明全部变换、真实跨角色胜率或API模型质量；输入没有真实截图、游戏记录或主数据复制。

## 版本化打法资料接入

`HIRO_EXAM_STRATEGY_REFERENCES=1` 与显式身份模式一起启用可选资料层。`brain/strategy_references.py` 以准确主数据机制和明确考试阶段筛选 `defaults/strategy_refs/*.json`；当前仅有好印象首考的内部候选资料，不适用于第二、第三考或本战。

资料包含来源、版本、适用条件、未知边界和内容 SHA-256，进入模型上下文，并在模型调用版本中保留引用标记。它只提供比较建议；合法动作、费用核对、后置规则仍按现有接口处理。Codex CLI 与 API 适配器使用相同上下文。

这是可追溯资料的加载接口，尚无自动经验提炼、策略自动升级或效果提升证明。下一步须在固定历史局面上比较原始模型选择与最终执行选择，区分模型变化、后置覆盖及状态识别错误，再决定是否启用资料。

## 既有硬规则的路线范围

第二考实测中，好印象路线剩 7 回合时模型选择加分饮料，被 `exam_policy` 的旧 R3“剩 4 回合以内才喝”规则覆盖。该记录证明发生了跨路线覆盖，不证明喝饮料本身最优。显式身份模式现通过主数据 `recommended_effect` 将整组旧干劲经验规则限定到干劲路线；其他路线/身份未知时，有预演只按已提供的合法动作预演排序，无预演不套旧预算、留牌及冲突牌规则。通用合法性、实际支付条件及执行前画面核对仍保留。关闭显式身份模式时，原策略行为保持兼容。

## 当前实测中的共享状态修复

- 第十天体力画面为 26/45，但原 OCR 在 native 尺度读成合法的 2/45 并提前返回，造成误选休息。现核对两尺度；冲突时独立重读当前值和上限，不能达成一致则保留未知。该真实帧离线修复后为 26/45。

- 这些修复不依赖角色或流派。决策质量比较必须先排除识别和状态记账错误，不能把由错误输入导致的动作归因为某套角色打法不好。

## 免费强化选择（尚未实机验收）

`HIRO_MECHANISM_ENHANCE=1` 为默认关闭的机制比较器，只用于已打开且有明确 P 道具/免费事件来源的强化页。比较准确基础版与强化版的完整效果、费用和条件，结合当前构筑考虑升级增量；不按角色名或卡牌编号排序，也不自动打开商店或支付 P。

现执行器仅按 `card_id` 找卡，无法可靠区分同 ID 的不同副本，因此模型候选排除重复 ID、未知版本和已知定制但效果不明的卡。强制页失败等待，只有明确允许取消的事件页才能取消。当前只有合成测试，没有真实强化选择页证据；自动强化结果画面不算本功能验证，运行脚本尚未启用此开关。

## 授業换卡与轮间决策

第十七天第二阶段的实扫发现历史账本失真：全局最后一次完整查看是第1天8张，随后账本按事件增长到17张，但第二考实际手牌已经出现未入账牌。不能从缺失日志猜获得/删除原因。当前重新从首顶滚到尾底，识别18张且无未知；低特征卡通过唯一选中角框及详情精确名称补读，不降低卡面匹配阈值。

数量链证明不再替代版本与定制可信度。Windows 开启 `HIRO_DECK_REVIEW`：续跑牌组先待复核、考试结算后要求新查看，确认完整后才恢复可信；定制标记保留，具体定制效果未知。换卡第二阶段可以在已观察到的固定换入卡与完整新牌组上显式重新评估换出目标，支持进程重启和旧计划失效；不能缺少证据时沿用旧目标。

第十七天换卡实测已完成：恢复进程在第二阶段扫描18张完整牌组，模型显式重新评估并选择ファンサの基本+→夢色リップ+，游戏结果文字确认替换，事件账本保持18张并正确继承强化版本。该结果验证恢复、决策与执行链路，尚不证明分数收益或跨角色策略质量。选中框检测发现相邻列会累计到另一张卡的角框像素，现要求目标卡四角分别成立；四张实帧正负例验证通过。决策及事件记录同时补齐换入卡和继承强化版本，删除旧卡按精确版本匹配，避免同名不同强化的牌组记录被误改。

共享非考试上下文增加固有卡基础/强化版和身份关联道具效果，均标为主数据定义；实际装备、触发次数和定制仍未知。饮料选择也使用同一份牌组可信度及机制上下文。已确认事件链恢复的牌组仍可用，不能仅因来源标记是续跑推断就丢掉已有核验证据。

第十七天实机授業并非可以用“麻烦牌档不换卡”绕开：逐项单击预览确认，三档都是换卡，分别限定好印象、限定干劲、不限定路线且追加麻烦牌。`produce/study_preview.py` 只单击当前未选中的选项，核对选中态并记录每档效果与观察序号；单击未生效即停止，不能补点变成确认。四行效果框的参数增益首行也纳入识别。预览已经在当前窗口验证，尚未因此确认换卡。

`HIRO_MECHANISM_CHANGE=1` 接入两阶段成对比较：依据完整可信牌组和准确卡版本，先比较换入/换出组合，再核对实际目标。不用旧路线价值表代替模型选择；观察或执行映射不明确时等待。进入前仍无法看到随机换入候选，牌组可换不等于保证本次换卡有收益。

`HIRO_MECHANISM_INTERVAL=1` 接入货架购买及回复档位比较，共用模型接口和当前预算验证。启用后，“结束”不会再触发旧执行器的隐式回血消费。尚不覆盖轮间强化、定制、刷新；未观察到硬性补卡数量，不能把旧攻略的 22 张作为游戏硬约束。该模块目前只完成离线验证，尚未实机验收。两个开关均默认关闭。


## 第十九天定制入口与待补能力

实机 r12 进入特別指導时旧入口判定超时，但随后确认游戏已经在选卡页；不能再根据旧 ACTION_SELECT 候选改点休息。入口改为正向识别选卡/定制菜单，确认后独立等待且至少读取两帧；不确定时停止。由于标定目录没有保存到帧，具体超时时序未证实，延迟转场与慢 OCR 情况由定向回归覆盖。

通用定制尚未接通：需要保存预览图并核对准确卡版本、物理菜单列、当前/之后效果、实际价格与剩余次数，执行前重新验证。现有菜单漏项会导致紧缩编号；旧执行器不复核价格和完整效果，且返回一览可能结束该卡的定制机会。应在菜单会话内逐次观察与决策，而非盲循环固定等级。当前非干劲路线不会套用旧固定卡表。
